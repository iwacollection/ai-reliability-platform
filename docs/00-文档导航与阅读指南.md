# AI Reliability Platform 文档导航与阅读指南

> 本文是 `docs/` 的总入口。目标不是罗列文件，而是告诉读者：这个平台为什么这样设计、各模块解决什么问题、当前代码做到什么程度，以及应该按什么顺序理解整个系统。

## 1. 项目定位

AI Reliability Platform 是一个面向 SRE / DevOps 的 **Evidence-driven、Human-in-the-loop、Agent-first Reliability Agent**。

核心闭环：

```text
事件进入
  ↓
Incident 建立
  ↓
理解当前状态
  ↓
发现证据缺口
  ↓
主动调查
  ↓
形成假设
  ↓
证据验证
  ↓
生成结构化动作计划
  ↓
策略检查 / 人工审批
  ↓
安全执行
  ↓
恢复验证
  ↓
Incident 关闭
  ↓
轨迹审计 / 评估 / 经验沉淀
```

平台的核心不是“让大模型回答运维问题”，而是让模型的决策能力进入一个**有状态、有预算、有权限、有证据、有恢复能力的运行时**。

## 3. 文档中的三个状态标签

文档必须区分：

- **当前实现**：代码仓库已经存在并可以验证。
- **当前基础 + 生产增强**：仓库已有基础实现，但生产还需要进一步强化。
- **目标设计**：用于描述未来能力，不能当作已经实现的功能。

禁止把目标架构写成“已经生产可用”。

## 4. 核心概念关系

```text
StandardEvent
    ↓
Incident
    ↓
Context
    ↓
Agent Loop
    ├── Evidence
    ├── Memory
    ├── Tool / MCP
    └── Change
            ↓
       Diagnosis / Plan
            ↓
       Policy / Approval
            ↓
          Action
            ↓
       Verification
            ↓
       Audit / Evaluation
```

### Incident
一次需要平台持续处理的问题实例。

### Context
当前 Agent 做下一次决策真正需要的工作集，不等于聊天记录。

### Evidence
来自系统、工具或外部数据源的可追溯事实。

### Hypothesis
Agent 当前对根因的解释。它必须与 Evidence 区分。

### Tool
Agent 可以调用的能力。Tool 本身不应该决定业务流程。

### Action
改变系统状态的结构化意图。

### Verification
判断 Action 后系统是否真正恢复，而不是判断 API 调用是否返回成功。

## 5. 设计原则

### 5.1 Agent-first
不要把所有故障写成固定 Workflow。Agent 根据目标、状态和证据选择下一步调查。

### 5.2 Evidence-driven
没有证据支持的结论只能是候选假设，不能自动升级成生产动作依据。

### 5.3 Runtime-enforced
不能依赖 Prompt 保证安全。权限、参数、风险、审批、预算和停止条件必须由 Runtime 强制执行。

### 5.4 Read 与 Write 分离
调查工具默认只读；修改系统状态的 Action 进入独立安全链路。

### 5.5 Execute 与 Verify 分离
执行成功不代表系统恢复。必须通过独立 Verification 判断最终状态。

### 5.6 可恢复
Agent 是长任务。Runtime 重启、工具失败、模型超时、审批等待都不能让 Incident 状态丢失。

### 5.7 可解释
任何关键决策都应该能够回溯：当时看到了什么 Evidence、调用了什么 Tool、为什么选择该 Action、谁批准、最终验证结果是什么。

## 6. 生产能力检查清单

```text
[ ] 事件是否可幂等接收
[ ] Incident 是否有唯一 ID
[ ] 状态是否持久化
[ ] Agent 是否有最大轮数
[ ] 是否有 Tool Call / Token / 时间预算
[ ] 是否有重复调用检测
[ ] 是否有无进展检测
[ ] Tool 参数是否经过 Runtime 校验
[ ] 权限是否与模型输出分离
[ ] 风险是否由平台重新计算
[ ] 高风险 Action 是否必须审批
[ ] Action 是否具备幂等性
[ ] 是否存在明确回滚策略
[ ] 执行环境是否隔离
[ ] Verification 是否独立于 Action 成功状态
[ ] Evidence 是否有来源、时间和引用
[ ] 是否可以完整恢复 Incident 轨迹
[ ] 是否可以 Replay
[ ] 是否可以对 Agent 行为评分
```

## 7. 最终应该形成的能力

一个真正可靠的 Incident Agent 不应该只是：

```text
告警 → LLM → 答案
```

而应该是：

```text
告警
 ↓
确定目标
 ↓
知道当前缺什么证据
 ↓
主动调查
 ↓
验证假设
 ↓
知道自己什么时候不能继续
 ↓
提出结构化动作
 ↓
经过安全控制
 ↓
执行
 ↓
验证结果
 ↓
如果失败继续调查 / 回滚 / 升级人工
 ↓
最终形成完整证据链
```

这就是本仓库所有模块存在的共同原因。
